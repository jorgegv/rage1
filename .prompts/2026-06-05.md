# Tasks

## Task 1: debug movement in CPC (moved from 2026-05-31, PARKED)

- make build-minimal_cpc: the hero moves (using QAOP), but in 8-pix increments (looks like)

### Resolution

NOT a code regression. gfx_cpctel.c (gfx_cpctel_move_sprite_clipped) intentionally
quantises sprite position to the 8x8 cell grid (col = x>>3, row = y>>3): the
documented G8 "cell-granular movement" functional bar.

Investigation: pixel-smooth CPC movement was never contemplated in the plan
(G8-5 set only a *functional* bar). No CPC sprite library (cpctelera, z88dk
CPCRSLib, cpcsprite, AMSprite) offers 1px HORIZONTAL positioning — all are
byte-aligned (M0=2px, M1=4px, M2=8px); vertical 1px is free. 1px horizontal
needs pre-shifted / runtime-shift / compiled sprites, always built by the engine.

DECISION (parked): pre-shift rejected (too memory-heavy). Will instead add CPC
support to JSP (Jorge's sprite lib) using realtime shifting + masking (SP1/JSP
model), then use JSP-in-CPC-mode as RAGE1's CPC sprite engine. RAGE1 CPC sprite
work is PARKED until JSP-CPC lands; gfx_cpctel cell-granular stays as the interim
backend. See memory project_cpc_sprite_engine_via_jsp.

## Task 2: redo plan with JSP-CPC sprite engine

Context:
- In previous tasks we found that the sprite engine we had decided upon (cpctelera) moved in byte coordinates, that it, 2px (mode 0), 4px (mode 1), 8px (mode 2) increments.
- This is not acceptable at all. A sprite engine for RAGE1 must be able to move sprites in 1px precision
- Due to this, we parked the RAGE1 CPC port until we had a JSP port for CPC.
- Today we have that port. JSP has received full CPC support and is available

Work to do:
- Since changing the sprite engine is a groundbreaking change, we need to reevaluate the whole plan taking into account the switch to JSP-CPC
- Read thoroughly the JSP documentation about the CPC modes using ultrathink and analyze which parts of the project would affected
- Since JSP-CPC has several modes of operation, use MODE-1 in regular mode (_NOT_ MONO mode) as the initial mode to use for the RAGE1 port. We will add support for the other modes later.
- JSP-CPC also has a tool for generating sprite and tile assets in all modes, with the proper format compatible with the engine. Given that we can create functions to setup the video modes if needed (the demo programs for JSP-CPC already do it), the Arkos tracker is directly supported by RAGE1 (not using the one from CPCtelera), the sprite engine is _not_ cpctelera's, and that we may reuse the input layer from z88dk (can we?), consider the possibility of REVOKING cpctelera as the graphical CPC engine, and instead just use JSP and whatever we need to develop or use.
- Review/modify the current plan according to this, do not change code
- After finishing the plan revamp, review with an independent agent until agree
- Consider in the plan the rewrite of the cpc test games to be as similar to the ZX ones as possible. Try to reuse the assets. Maybe you need to create PNGs from some assets created in text mode so that CPC tools can extract them and generate CPC-format assets.

After JSP-CPC support is in place, most probably Task #1 will be superseded as N/A

### Completion notes

The submodule bump (Task 2, pin 6037d71) reorganised JSP's tree into
`lib/` (shared) + `lib/zx/` + `lib/cpc/` (was a flat `lib/`). RAGE1's
`Makefile.common` JSP wiring only globbed `lib/*.asm`, so it stopped pulling the
ZX platform layer (`lib/zx/*.asm`: jsp_redraw/screen/draw_*/covered/frame/…) —
the ZX JSP build broke (undefined `_jsp_redraw`, `_jsp_move_sprite`,
`jsp_rowcolindex_dtt`, …). Fixed by making the JSP wiring **platform-aware**
(ZX → `lib/zx/*.asm`; CPC → `lib/cpc/*.asm` + JSP CPC flags). Verified by user:
`minimal_jsp` and `default_jsp` (ZX) build and run correctly after the update.

### Decisions (from 2026-06-06 chat review)

- **Copy/adapt, do NOT share** cpcgfx.pl. cpcgfx.pl stays in the JSP submodule,
  untouched; datagen owns its own CPC packing (adapted from cpcgfx.pl's
  `cell_bytes`/`emit_cell`). Contract = the generated **bytes** stay
  JSP-compatible; the code may diverge. (User's call — sound given the
  RAGE1↔JSP repo/submodule boundary; supersedes my "shared module" idea.)
- **#1 module location → `lib/RAGE/`** (RAGE1's existing convention,
  `use lib "$FindBin::Bin/../lib"`, namespace `RAGE::`), NOT a new `tools/lib`
  (that's JSP's convention). Supersedes the earlier "tools/lib" bullet above.
  e.g. `RAGE::AssetBackend` (registry), `RAGE::AssetBackend::ZX`,
  `RAGE::AssetBackend::CPCMode1`, `RAGE::CPCGfx` (copied packing core).
- **#3 verification gate → ZX byte-identical.** After the ZX-backend
  extraction, `make all-test-builds` + `tests/00regression/` must be green and
  ZX output byte-identical, BEFORE adding the CPC backend.
- **Compatibility safeguard** (my refinement, accepted): a regression test that
  proves datagen's CPC Mode-1 output is byte-identical to cpcgfx.pl's output for
  the same reference art — turns "stays compatible" into a verified invariant
  without coupling the code.
- **Supersedes A8's subprocess + PIXELS→PNG bridge**; **reverses cross-doc
  decision §5.1** (CPC encoding now in-datagen Perl, not a subprocess — fine now
  the encoder is JSP's own Perl, not cpctelera's C/asm). To be recorded in
  README §5.1 / §5.13b + assets.md A8.
- Gating piece for **R9** (clone minimal_jsp→minimal_cpc; animated hero on CPC).
- **#2 heavy-refactor depth → DECISION: option A (2026-06-06).** Do **Stage 0 +
  Stage 1 now**, **defer Stage 2** to a separate, incremental future pass.
  - **Stage 0** (cheap leaf modules, byte-identical): e.g.
    `RAGE::Datagen::ColorTokens` (colour vocab + `_cpc_fw_color_for` +
    `_parse_zx_attr_tokens`).
  - **Stage 1** (the task's core — the asset-backend seam): `RAGE::AssetBackend`
    (registry/interface) + `RAGE::AssetBackend::ZX` (move `pixels_to_byte` + the
