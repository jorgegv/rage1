### Step 10 ROOT CAUSE FOUND (2026-06-11, via border-probe/freeze bisection)

**The cold-boot LOADER never populates the dataset expansion bank (RAM5).** The
engine boots, reaches `run_main_game_loop` → `game_state_reset_initial` →
`map_enter_screen` → `dataset_activate` → `memory_switch_bank(5)` (OK) →
`dzx0_standard` decompress — which reads an EMPTY RAM5 (a 4-way border probe at
the dataset source `0x4050` read `0x00` = blue), runs away, overruns 0x8000 up
into screen RAM (0xC000), crashes → ~1 s reboot loop. So the "garble/trails" was
never a render bug.

Ruled OUT en route (do not re-investigate): NOT interrupts-during-decompress
(crashes with `di` too — removing "Fix A" is exonerated); NOT a render-time
window-shadow (loop body never runs); NOT bad compressed data (BANK5.BIN[80:128]
== dataset_0.zx0, decompresses to 76 B offline); NOT the `memory_switch_bank`
primitive (cpc-bswitch-test passed). The bug is in `engine/loader-cpc-banked/`'s
streaming: it CAS-loads BANK5.BIN to staging 0x9000 then DI/Config-5/LDIR→0x4000,
but RAM5 ends up empty. See memory [[cpc-banked-z88dk-banking-model]] /
[[cpc-banked-dataset-loader-session]] — the staging+LDIR premise was already
flagged WRONG; "direct CAS to 0x4000 under Config C4-C7 works" (z88dk-proven).

(jsp_bat 0x9800 … jsp_rottbl 0xB200) should be page B 0x6000-0x7FFF; SP=0x9800

### Step 10 ROOT CAUSE REFINED (2026-06-11 PM, loader-side screen-fill bisection)

The empty-RAM5 chain is now pinned to an EXACT instruction. Method: temporary
screen-fill+freeze probes inserted into the loader templates (0xFF fill →
visibly RED in cap32 = "reached"; uniform BLUE = "not reached / CRT-cleared";
distinct 0xF0 fill on `_loader_error`). Headless cap32 read via histogram (no
user-in-the-loop needed — screen fill is captured, unlike the border). Results:

- proof-of-life at `_main` entry → RED (loader runs).
- after GAME.BIN OPEN/DIRECT/CLOSE → RED (first file loads fine).
- after BANK5.BIN CAS_IN_OPEN → BLUE, and NOT `_loader_error` (0xF0) → the
  second `CAS_IN_OPEN` HARD-CRASHES the firmware (no carry-clear error return).
- ISOLATION: opening BANK5.BIN FIRST (before GAME.BIN) → RED. So it is NOT
  BANK5-specific and NOT a bad file/filename — it is the SECOND sequential
  firmware CAS operation that crashes.

ROOT CAUSE: the loader drives the AMSDOS CAS routines through z88dk's `firmware`
process-exx interposer (`call firmware / defw 0xBCxx`) while in PROCESS exx
state. One file works; a second sequential `CAS_IN_OPEN` crashes — the
per-call fw-state swap does not preserve the AMSDOS subsystem state across
open→direct→close→open. z88dk's own `lib/target/cpc/classic/loader.asm` loads 8
bank files sequentially with DIRECT `cas_in_open/direct/close` ($bc77/$bc83/
$bc7a) calls, but does so in NATIVE firmware exx state at crt0 (`cpc_crt0.asm`:
kl_rom_walk L101 → loadbanks L112 → cpc_enable_process_exx_set L124 → main) —
i.e. ALL CAS happens before the process ever seizes the alt-register set.

⇒ This is exactly the two-CRT / firmware-state seam flagged in memories
[[cpc-banked-z88dk-banking-model]] and the §6 direct-vs-interposer note. The
loader's header comment ("direct call routes to TAPE") is true only in PROCESS
state; z88dk proves direct CAS works in NATIVE state.

FIX ATTEMPT 1 (native exx state + direct CAS, in _main) — INSUFFICIENT (tested):
  Implemented `di / call cpc_enable_fw_exx_set / ei` at _main + DIRECT $bcxx calls
  + reorder (banks first, GAME.BIN last).  Re-bisected on cap32:
  - cpc_enable_fw_exx_set + 1st direct CAS (GAME.BIN open/direct/close) → RED (ok).
  - But the loader STILL crashes.  Refined bisection nails the exact rule:
    * A large CAS_IN_DIRECT (GAME.BIN ~22 KB) works ONLY as the FIRST CAS op.
      GAME-direct as a 2nd op (after a bank load) → crash.  GAME-OPEN as 2nd op
      → RED (ok), so it is the large DIRECT, not the open.
    * After a large direct (as 1st op), the next CAS_IN_OPEN also crashes.
    * Small ops chain fine (small direct + 2nd open = RED).
  ⇒ Only the FIRST disc transaction is reliable.  cpc_enable_fw_exx_set restores
  the exx set + ISR vector but NOT the full firmware EVENT/TIMER state that the
  loader's own crt0 already disturbed at startup (cpc_enable_process_exx_set) — so
  the 2nd motor spin-up / multi-track seek faults.

FIX ATTEMPT 2 (custom loader crt0, PRISTINE state + direct CAS) — also INSUFFICIENT:
  Implemented crt0-cpc-banked-loader.asm = stock +cpc cpc_crt0 MINUS the single
  `call cpc_enable_process_exx_set`, so the loader NEVER seizes the firmware
  exx/ISR state; _main loads with DIRECT $bcxx calls (no `firmware` interposer);
  wired via -crt0= in Makefile-cpc-banked.  Re-bisected on cap32:
  - custom crt0 reaches _main → RED.  GAME.BIN load (1st op) → RED.  But the bank
    CAS_IN_OPEN (2nd op) STILL crashes (BLUE).  ⇒ exx/event-state was NOT the cause.

ROOT CAUSE (final, exx-INDEPENDENT): a LARGE CAS_IN_DIRECT (GAME.BIN ~22 KB) can
  only be the SOLE CAS transaction.  Any CAS_IN_OPEN BEFORE or AFTER it crashes
  the firmware; a large direct as a NON-first op also crashes.  Small files chain
  fine (small direct + 2nd open = RED).  Confirmed in BOTH disturbed (stock crt0)
  and pristine (custom crt0) state — so it is NOT the exx/ISR seize.  It is the
  large multi-track AMSDOS read itself poisoning the FDC/disc state for any other
  CAS op.  z88dk never hits this: its MAIN IMAGE is loaded by the AMSDOS RUN"
  (firmware), and only the SMALL bank files go through CAS (loadbanks).

IMPLICATION: the current packaging model 2 (separate LOADER.BIN that CAS-loads BOTH
  the big GAME.BIN AND the banks) cannot work for any game that has banks.  The
  large GAME.BIN must NOT be loaded by a CAS_IN_DIRECT that is followed/preceded by
  other CAS ops.

  `-create-app -subtype=dsk` invokes) auto-emits one disc file per POPULATED

  problem never arises (main image is loaded by RUN", not our CAS).

  and bank_N.bin offset-0 convention — exact match, no re-layout needed.
- A bank is "populated" iff `__BANK_n_size`>0 (appmake mb_enumerate_banks,
  appmake.c:1191+). Incbin pattern confirmed: `SECTION BANK_n` + `BINARY "f"`
  (examples/sms/3dcity/content/music.asm).
- **Foundation already in tree:** zpragma-cpc-banked.inc sets `MMAP=-1`;
