### Coverage assessment per input touch-point named in IN1-1

The spec (input.md lines 975-983) names three input flows that the
baseline should pin:

1. **Controller-selection menu flow in `games/default`** (key '1' →
   keyboard).
   - **Status: indirectly covered.** The `default` test injects SPACE at
     frame 700 to dismiss the loading screen and screenshots at frame
     1000. The captured frame depicts the per-game menu rendered by
     `games/default/game_src/game_functions.c` after
     `init_controllers()` has already initialised the engine
     controller state. The keyboard '1' selection itself is not
     replayed (the runner injects only SPACE), so the snapshot pins the
     **menu render** rather than the post-selection branch.
   - The same per-game menu is also exercised by `blobs`, `crumbs`,
     `damage_mode`, `get_weapon`, `monochrome`, `vortex2` (all 128k,
     same script). The 48k counterparts (`minimal`, `mapgen`,
     `sub_bufs_48`) snapshot their own menus with no key press.
   - **Effect on Phase IN3 migration:** swapping
     `engine/src/controller.c`'s `<input.h>` include for the new
     `rage1/input.h` HAL is safe to validate against this baseline —
     any regression in the menu render (font, attribute, sprite
     overlap) would show up as a pixel diff at frame 700/1000 in all
     eight 128k tests. The HAL must keep the pre-keypress menu
     identical.

2. **Game pause logic (press Y while in game).**
   - **Status: NOT covered.** None of the 12 `test.conf` files inject
     'Y' (or any pause key) once the game loop has started. The closest
     they get is SPACE at frame 700 to dismiss the loading screen.
     `controller_pause_key_pressed()` (defined in
     `engine/src/controller.c`) and the pause branch in
     `engine/src/game_loop.c:39-43,112-114,230` are therefore not
     under regression at this baseline.
   - **Phase IN3 follow-up (not IN1):** the pause path is the most
     visible behavioural change risk in IN3, since the pause poll
     happens every frame and is the only `in_*` call that runs in the
     hot loop. A dedicated regression test that injects 'Y' at a frame
     where the game is in steady state (e.g. frame 1500 on `default`)
     would close this gap. **Tracked as Phase IN3 follow-up.** Not
     added in IN1 per spec.

3. **Hero-fire edge detection** (`engine/src/hero.c:170,183,190`
   reading `game_state.controller.state & IN_STICK_FIRE`).
   - **Status: NOT directly covered.** The baselines do not press the
     fire button or any movement key during the captured frame window.
     The fire edge-detection code path is reached only when
     `controller_read_state()` returns a state with the FIRE bit set,
     which requires a key/joystick press the runner never sends.
   - **Phase IN3 follow-up (not IN1):** a regression test on
     `get_weapon` (the game whose name implies weapon-pickup logic) or
     on `damage_mode` (which exercises projectile/damage interactions)
     that injects FIRE for a few frames mid-game would close this gap.
     **Tracked as Phase IN3 follow-up.** Not added in IN1 per spec.

### Phase IN3 follow-up checklist (not done in IN1)

The two gaps above are **not** closed in Phase IN1 (the spec is
explicit: "If a critical input flow is genuinely uncovered (e.g.
in-game pause behaviour), document that as a Phase IN3 follow-up —
don't add tests in IN1"). They are recorded here so Phase IN3 can pick
them up:

- [ ] **IN3-followup-1** Add a regression test that injects the pause
  key (game-defined, typically 'Y' on `default`) at a steady-state
  in-game frame and screenshots one frame later, to pin the pause
  overlay/state-freeze behaviour. Candidate game: `default` (128k) or
  `minimal` (48k, simpler).
- [ ] **IN3-followup-2** Add a regression test that injects the fire
  key during gameplay on a game where a fire press has a visible
  one-frame side effect (bullet sprite spawn, weapon swap), e.g.
  `get_weapon` or `damage_mode`.

Both follow-ups can re-use the existing `regression.sh` harness — they
just need new `tests/00regression/<name>/test.conf` files with the
appropriate `EXTRA_ARGS` keypress sequence and matching reference PNGs
captured against the IN1-pinned engine code.

## IN1-2 — `kbd.c` / `kbd.h` per-game duplicate inventory

### Inventory (from `find games -name "kbd.*"`)

```
games/default/game_src/kbd.c
games/default/game_src/kbd.h
games/default_jsp/game_src/kbd.c
games/default_jsp/game_src/kbd.h
```

Exactly **two games** carry `kbd.c`/`kbd.h` — `default` and
`default_jsp`. Confirms the spec (input.md lines 99-101). No other
test game in `games/` ships either file.

### Diff result

- `diff games/default/game_src/kbd.c games/default_jsp/game_src/kbd.c`
  → **zero output** (files are byte-identical).
- `diff games/default/game_src/kbd.h games/default_jsp/game_src/kbd.h`
  → **zero output** (files are byte-identical).

### Significance

Both files are not just "near-identical" (as input.md §1.1 currently
says) — they are exact duplicates today. This is the known
consolidation surface for Phase IN4: the entire `capture_key_scancode()`
helper (one C function with inline Z80 keyboard-scan ASM) can move into
the engine (or into a shared per-platform helper directory) without
behavioural risk, and the two per-game copies deleted in lockstep. The
implementation hard-codes the 8 ZX row ports `{0xf7,0xfd,0xfb,0xfe,
0xef,0xdf,0xbf,0x7f}` and `IN ($FE)`, so the consolidation will need to
land behind a ZX-only guard (`BUILD_FEATURE_PLATFORM_ZX*` or the
equivalent platform token established in Phase 2 A1) once the input HAL
gains a CPC backend.

No divergence to flag.

## IN1-3 — Static-grep CI guard for `<input.h>` in banked code

### Allowed-list freeze (re-grepped, frozen as of IN1 exit)

`grep -l '<input.h>' engine/banked_code/common/*.c engine/banked_code/128/*.c`
returns exactly one file:

```
engine/banked_code/common/hero.c
```

This is the single allowed exception under `engine/banked_code/`. The
guard treats any *other* file under `engine/banked_code/` (recursive)
that `#include`s `<input.h>` as a regression and exits non-zero.

(For context: the wider engine surface also `#include`s `<input.h>` from
`engine/src/controller.c`, `engine/src/game_loop.c`, `engine/src/debug.c`,
`engine/src/main.c`, and `engine/src/hero.c`. Those live outside
`engine/banked_code/` and are NOT covered by the IN1-3 guard; their
migration is the subject of Phase IN3 and is tracked there. The IN1-3
guard is deliberately narrow — its purpose is to stop the banked-code
include surface from growing during the refactor.)

### Implementation

- Script: `tools/check-input-include-guard.sh` (new, IN1-3).
- Wired in `Makefile` as the `.PHONY` target `check-input-includes`.
- Greppable spec of the allowed list: a single literal-path constant
  inside the script (`engine/banked_code/common/hero.c`).
- Exit code: `0` if banked-code `<input.h>` includes match the allowed
  list exactly; `1` if any new file violates, with a diagnostic
  listing the offending paths.
- The guard is non-destructive: it never modifies files, only inspects
  them with `grep -rl`.

### Phase-exit verification

Run at IN1 exit (must be `0`):

```
make check-input-includes
make all-test-builds
```

Both must be green for IN1 to be considered complete.
